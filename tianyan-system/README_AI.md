# 天眼系统 AI 项目说明

> 本文档用于让维护人员或其他 AI 以当前目录为项目根目录快速接手。文档基准日为 2026-07-24；实时数据水位、运行状态和发布版本必须读取数据库、节点结果与远端版本，不得使用文档中的历史数字代替检查。

## 1. 系统职责

天眼系统负责：

1. 增量采集天天投顾、广发基金、广发证券和且慢的投顾策略基础信息、业绩、风险、当前仓位和调仓。
2. 维护全市场公募基金、FOF、基金净值、基准、分类、持仓和穿透数据。
3. 将通过渠道批次验收的数据事务化写入 SQLite 主库，并治理策略生命周期、重复调仓、绩效和可比分类。
4. 生成策略列表、详情、对比、AI 选策略、投顾与 FOF 排名、调仓月报等业务页面。
5. 数据稽核通过后生成成功数据库备份、最小发布集并验证 GitHub Pages 版本。

当前每日增量覆盖 `ttfund`、`gffunds`、`gfsec_fima`、`gfsec_robot` 和 `qieman`；广发银行历史数据保留但暂停每日采集。

## 2. 运行原则

- 根目录唯一生产入口是 `00_每日数据更新并发布_唯一入口.bat`。
- 所有内部路径相对工作区根目录解析，不允许固定盘符或 `..` 路径逃逸。
- 两台电脑或两个进程不得同时执行每日更新。
- 采集先写运行批次，渠道批次验收通过后才允许标准化和入库。
- 主库写入使用事务；失败批次不得形成半批业务数据。
- App 原始披露优先。原始当前仓位不可得时才允许推算，并必须记录来源和缺口。
- 关键节点失败后不得创建成功备份、覆盖正式结果或发布。
- 发布失败保留 `data_success_publish_failed`，恢复时只执行仍需重跑的交付节点。
- 不得用模拟值填充真实数据缺口，也不得为了通过稽核删除、跳过或弱化规则。
- 当前每日交付范围固定为最小发布包；完整报表系统保留最近一次已验证版本，非最小发布内容暂停刷新。
- 可披露覆盖率缺口和 Pages 传播延迟只记 warning；页面缺失、解析错误、净值尺度异常、数据库损坏和事务失败仍阻断对应下游。

## 3. 两种布局

同一套代码支持两种目录布局。

### 3.1 开发工程

当前目录本身就是 `codeRoot`。数据库、原始数据、日志和开发结果通常位于 `data`、`logs`、`outputs`、`site`。

### 3.2 迁移运行工作区

`本机配置/runtime.local.json` 存在且 `codeRoot` 为 `程序代码` 时，目录职责如下：

```text
天眼系统/
  00_每日数据更新并发布_唯一入口.bat
  AGENTS.md
  README_AI.md

  程序代码/
  本机配置/
  数据库/
  采集数据/
  运行状态/
  结果文件/
  数据库备份/
  迁移基线/
  运行环境/
```

根目录可见文件只能是唯一 BAT、`AGENTS.md` 和 `README_AI.md`；Git 隐藏项允许保留。程序更新只覆盖 `程序代码`，不得覆盖其他运行数据目录。


## 5. 唯一入口

双击或不带参数运行时直接更新最新数据：

```bat
00_每日数据更新并发布_唯一入口.bat
```

运维模式：

```bat
00_每日数据更新并发布_唯一入口.bat initialize
00_每日数据更新并发布_唯一入口.bat check
00_每日数据更新并发布_唯一入口.bat resume <run_id>
00_每日数据更新并发布_唯一入口.bat resume <run_id> --from-node <node_id> --to-node <node_id>
00_每日数据更新并发布_唯一入口.bat node <node_id> --run-id <run_id>
```

- `initialize`：安装或检查环境，创建运行布局并执行初始化检查。
- `resume ... --from-node ... --to-node ...`：校验并复用起点之前的成功产物，从起点实际重跑，并在终点成功完成后结束；适合只恢复到稽核、备份等明确边界，避免误触后续发布。
- `check`：不采集数据，只检查环境、数据库、设备、Git 和网络。
- `resume`：验证已成功节点的输入指纹、结果文件和校验器，从首个无效节点继续。
- `node`：执行目标节点及其必需依赖，数据库写节点不能绕过前置批次验收。

运行工作区缺少 Python 3.12 环境时，启动器调用 `install_runtime_environment.ps1`，通过 `winget` 检查或安装 Python、Git、Node，并建立工作区虚拟环境。

## 6. 每日 DAG

日常链路共 28 个正式节点，渠道分支在预检后并行，批次通过后汇入统一加工：

1. `preflight_environment`：环境与依赖。
2. `preflight_database`：SQLite 健康和写锁。
3. `source_readiness`：最新披露就绪检查，未就绪每 30 分钟重试，最多 6 次。
4. `device_select`：仅预检配置的实体手机，本批次所有 App 采集和补采固定使用该真机。
5. `ttfund_incremental`：天天计划、接口、仓位、调仓、曲线、失败重试和批次验收。
6. `gffunds_performance`：广发业绩曲线。
7. `gffunds_metadata`：广发基准与费率元数据。
8. `gffunds_collect`：广发当前仓位与调仓。
9. `gffunds_gate`：广发失败重试与批次验收。
10. `gfsec_fima_collect/gate/load`：广发证券财富管家目录、事实、验收和事务入库。
11. `gf_supplemental_collect/gate/load`：广发证券贝塔牛补充渠道采集、验收和事务入库。
12. `qieman_collect/gate/load`：且慢关键词目录重扫、净值与历史增量、新策略全历史、验收和事务入库。
13. `process_load`：汇总各已验收渠道并继续标准化加工。
14. `fund_nav`：新基金完整历史、已有基金增量净值。
15. `fund_lookthrough`：基金穿透和分类。
16. `index_benchmark`：指数、基准和资产映射。
17. `strategy_governance`：生命周期、业绩风险和广义权益分档治理。
18. `report_build`：在运行状态目录构建最小发布包需要的临时报表源，不覆盖完整正式报表。
19. `data_audit`：对本批最小发布源执行完整数据规则稽核；代码静态检查由变更上线 hook 执行。
20. `database_backup/publish/pages_verify`：成功数据库备份、最小发布和远端版本验证。

天天的 5 个内部业务阶段另有说明节点，不单独进入 DAG；当前复合采集器负责真机对象级首轮、失败对象同一真机第二批次补采和最终缺口汇总。

## 7. 节点状态与续跑

状态库是 `update_state.sqlite`。节点化新增并维护：

- `daily_update_node`：节点当前状态、输入输出指纹和最近结果。
- `daily_update_node_attempt`：每次尝试、设备、耗时、日志和错误。
- `daily_update_artifact`：产物路径、哈希、水位和校验结果。

节点状态为 `pending`、`running`、`success`、`warn`、`failed`、`skipped` 或 `invalidated`。退出码为 0 但输出验证失败仍是失败。上游输出指纹改变后，下游自动失效；有效上游不会因续跑而重复采集。

资源锁：设备采集使用 `device`，主库写入使用 `main_db_write`，发布仓库使用 `publish_repo`。天天和广发设备采集保持串行，主库写入、治理、稽核、备份和发布保持串行。

## 8. 日志与结果契约

```text
运行状态/logs/daily_update/<日期>/<run_id>/
  console.log
  events.jsonl
  summary.json
  summary.md
  nodes/<node_id>/attempt_01/
    console.log
    node_result.json
    artifacts.json
```

控制台与 `console.log` 同步显示总节点进度、当前节点、对象完成数/总数、节点耗时、总耗时、设备、重试和剩余项。长任务子程序应输出结构化 `PROGRESS` 行；没有对象级进度的旧程序会显示节点心跳，但应继续逐步改造成真实对象计数。

分析最近一次执行时：

1. 先读最新 `summary.json` 和 `summary.md`，确认最终状态和失败节点。
2. 读该节点最新尝试的 `node_result.json` 与 `console.log`。
3. 结合 `events.jsonl` 确认重试、设备切换和耗时。
4. 核对主库实际表数量和业务水位，不因整体失败推断主库完全未变化。
5. 核对成功备份、最小发布集 Git HEAD、本地与远端 `buildId`。

## 9. 数据目录

- 主分析库：`数据库/analysis_zh_current.sqlite`，开发布局对应 `data/analysis_zh_current.sqlite`。
- 原始证据：`采集数据/raw`；标准化输入：`采集数据/normalized`。
- 正式完整系统：`结果文件/全市场投顾分析平台`；当前每日任务不更新该目录。
- 最小发布仓库：`结果文件/最小发布集`。
- 成功备份：`数据库备份`，失败运行不得新增成功备份。
- 业务基线：`业务基线`，包括指数资产分类和原始排名模板。
- OCR 资源：`资源/OCR`。

主库是页面、报表和分析的权威业务数据源。修改表结构时必须同步检查 `schemas`、`config/runtime/runtime_compatibility.json`、数据库迁移、页面生成器和稽核规则。

## 10. 设备与数据口径

- 天天当前仓位：直接接口优先；接口不可用时由 App 采集；仍失败才推算并标记。
- 天天调仓：先探测最新调仓日期，只对 App 与系统不一致的策略补差异；系统无历史时补全量历史。
- 天天与广发对象失败：同一真机内宽松重试；首轮剩余失败项由同一真机执行第二批次补采，最终缺口不阻断其他对象。
- 广发基准和费率：元数据脚本优先，仅字段仍缺失时补协议 PDF。
- 且慢：不占用手机设备锁；目录每批重扫，旧策略净值与事件按已知水位增量下载，新策略同批补全历史。权重闭合的官方历史快照进入 `策略历史持仓`；发车指令比例仍作为信号事实，不当作组合存量仓位。
- FOF 排名源：报表构建按策略总数、数据更新日、FOF 净值日和真实输入文件判断是否需要刷新；页面文件刚生成不构成源数据过期，业务水位一致时复用已验收本地源。
- 基金净值：新基金补成立以来历史，已有基金按各自最新交易日补增量；空返回与失败必须分开。
- 最新披露日取数据源实际返回的交易日或净值日，不强行等于自然日。

## 12. 程序更新与迁移

- 程序代码与数据库、采集数据、日志、结果、发布仓库、本机配置完全分离。
- `runtime_update` 只允许 Git 快进，更新前确认无每日任务和本地修改；更新后执行兼容性、语法和节点框架测试。
- 更新失败恢复旧提交；`runtime_rollback` 仅在目标代码支持当前数据库 `user_version` 时执行。
- `migration_package` 按白名单复制代码和必要资源，主数据库通过 SQLite Backup API 生成一致性快照，并为程序、配置、基线和数据库生成哈希。高频变化的采集数据、结果、日志和归档不逐文件哈希，由批次验收、SQLite 检查和 Syncthing 完整性负责。
- `98_非生产工具` 不进入每日 DAG；`99_兼容入口` 只保留一轮旧入口转发，禁止新增生产依赖。

## 13. AI 接手清单

1. 阅读本文件、`AGENTS.md`、`节点脚本/节点索引.md` 和目标节点的 `SKILL.md`。
2. 确认开发布局还是迁移运行布局，读取 `本机配置/runtime.local.json`，不要猜路径。
3. 检查有无活跃运行、锁和设备采集；诊断不得中断正在运行的真机 ADB 任务。
4. 先定位失败节点和尝试日志，再下钻共享生产程序；不要先重跑整个链路。
5. 修改责任节点或共享源码，保持 `node_result.json`、进度和产物契约。
6. 执行最小相关测试、DAG dry-run、路径扫描和项目数据稽核。
7. 结论应区分已验证事实、合理推断、未解问题、业务影响和验证证据。
