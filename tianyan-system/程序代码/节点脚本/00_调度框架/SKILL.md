# 节点调度框架

## 目标

读取 `pipeline.json`，按依赖顺序执行节点，记录每次尝试、日志、结果、产物和数据水位，并支持失败续跑与单节点诊断。

## 输入与输出

- 输入：工作区根目录、运行模式、可选运行批次或节点ID。
- 输出：`运行状态/logs/daily_update/<日期>/<run_id>` 和 `update_state.sqlite` 节点状态表。

## 运行约束

- 根入口只调用 `启动.ps1`，业务命令只能放在节点目录。
- 节点退出码为0后仍必须通过 `node_result.json` 的输出校验。
- 关键节点失败后不得执行备份和发布。
- `pipeline.json` 中节点必须声明在其依赖节点之后；调度器仍会执行稳定拓扑排序作为防御，并在第一个节点启动前校验所选执行切片的依赖完整性，禁止长任务运行后才暴露顺序错误。
- 核心加工节点依赖可选渠道时，必须显式声明 `allowFailedOptionalDependencies: true`，使渠道局部失败可以保留既有数据并继续完成稽核与发布；不得让可选渠道以隐式依赖阻断整批。
- 30秒心跳必须同时展示当前阶段、整体完成度、阶段完成度、节点完成度、节点已运行时间和整体预计剩余时间；ETA优先使用最近真实成功批次的节点耗时，并标明无样本时为“待估算”，不得用超时时间伪装预测。
- 唯一入口完成后默认保留控制台窗口，确保最终结果、交付闭环和日志路径可见；无人值守调用需显式设置 `ADVISOR_KEEP_WINDOW_OPEN=0`，该设置只影响外层窗口，不影响调度器收尾和资源锁释放。
- 双击唯一入口时必须先展示可恢复批次，并由用户选择“续作推荐断点、重新执行或取消”。同一天存在多个未完成批次时，优先推荐已验证完成节点最多的批次，避免较新的短暂预检批次掩盖已经进入交付阶段的有效断点。
- 调度器在节点开始、节点结束和整批结束时写恢复点；长节点运行期间每 600 秒原子刷新 `resume_checkpoint.json`，并追加一条轻量 `resume_checkpoints.jsonl`。续作时重新校验已完成节点的 `node_result.json` 与产物；当前节点有内部检查点时继续，否则只重启当前节点，不回退重跑整批。
- 快捷命令：`continue` 续作推荐断点，`restart` 创建新批次；`resume <run_id>` 自动定位该批次首个未完成节点，仍支持显式 `--from-node` / `--to-node`。
