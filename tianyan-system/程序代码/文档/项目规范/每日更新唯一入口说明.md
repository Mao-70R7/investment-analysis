# 每日更新唯一入口说明

## 日常操作

每天只运行运行工作区根目录下的：

```text
00_每日数据更新并发布_唯一入口.bat
```

正式入口会读取 `本机配置/runtime.local.json`，程序、数据库、采集数据、运行日志、正式报表和发布仓库按运行布局分离。不要把开发目录下的 `basic_data` 当作正式结果。

## 稳定性原则

- 天天投顾和广发基金按渠道隔离。天天投顾数据源未就绪、设备不可用或采集失败时，广发公开接口仍会采集和入库；失败渠道保留数据库中的最近成功数据。
- 普通网络抖动、少量策略缺口、真机短暂抖动、可选覆盖项缺失、日志清理失败和备份空间不足只记 warning 或渠道级失败，不会在发生点直接终止整个 DAG。
- 主数据库健康、事务入库、后处理、最小发布源构建、核心数据稽核等关键步骤失败时，依赖节点会被明确标记为 `skipped`；只有清单中显式允许降级的渠道汇总节点可以越过失败的可选依赖。
- 覆盖率不满、同类排名缺失、备份空间不足及 Pages 边缘节点延迟属于可解释 warning；页面文件缺失、解析错误、错误净值尺度、数据库损坏和事务失败仍是硬失败。
- 每个节点必须原子生成 `node_result.json`。退出码为 0 但结果缺失、JSON 损坏、验证失败或产物哈希变化，都按失败或恢复时重跑处理。
- 恢复运行只复用输入指纹、结果内容和产物 SHA256 均有效的节点；残留 `running` 节点先标记为 `interrupted`，再使用新 attempt 继续。

## 渠道与入库

1. 数据源就绪检查是天天投顾渠道门禁；失败后会跳过其设备和采集分支，但不阻断只依赖数据库健康检查的广发公开接口。
2. 设备预检只接受 `runtime.local.json` 配置的实体手机，并最多复检 3 次；模拟器和本机回环 ADB 设备不进入生产链路。天天投顾采集使用父批次派生的精确子批次号；局部缺口由同一真机执行第二批次补采，最终仍缺失的对象进入 warning 和缺口清单，缺少基础基线才阻断天天渠道。
3. 广发业绩覆盖数据库及发现清单中的完整策略集合。历史调仓明细优先复用已验证缓存，只请求新增、缺失明细；最近一笔调仓默认每天刷新，同日重试可复用缓存。
4. 广发验收要求策略总量至少保留上批 90%，且业绩响应、调仓响应、最新基金仓位均至少覆盖本批策略的 95%；95% 至 100% 的可接受缺口和最新明细缓存回退记 warning，推荐基金列表属于可选覆盖，不再误杀核心批次。
5. 两个渠道分别使用精确批次、`BEGIN IMMEDIATE` 和回滚保护做增量 upsert。单渠道入库失败保留该渠道旧数据，不先删除再加载。
6. 两个渠道都没有成功入库且也不是“确认无变化”时，数据加工节点才会失败并阻止报表和发布。

## 报表、稽核、备份与发布

1. 每日只在 `运行状态/temp/minimal_report_source/<run_id>` 构建最小发布包需要的基础页面和报表源；`full_data_statistics_report`、`strategy_center`、广发独立监控页和 QD 独立专题页暂停更新。
2. 数据稽核只检查本批最小发布源。稽核有 error 时不发布；稽核通过或只有业务 warning 时，直接从该临时源原子构建最小发布包，正式完整 `reportRoot` 保留最近一次已验证版本且不被覆盖。
3. 数据库备份要求本批次 `process_load` 和 `data_audit` 成功，使用 SQLite 在线备份并执行 `quick_check`。默认保留最近 2 个成功版本，要求至少 45 GiB 可用空间。
4. 备份失败属于运维 warning，不阻断已经通过数据稽核的最小包发布；数据库、最小发布源或核心稽核失败仍会阻断发布。
5. 发布只读取已通过稽核的本批临时源，不读取开发目录，也不把临时源提升为完整正式报表；发布成功后立即删除临时源，失败源最多保留 2 份且最长 3 天。
6. 每日数据稽核不重复扫描全工程静态语法；静态语法检查属于代码变更上线门禁，仍由修改后的完整项目稽核 hook 强制执行。
7. 最小包构建、校验、HTTP 冒烟、Git 提交和推送属于发布硬门禁；GitHub Pages 远端传播验证是独立 warning 节点，网络或 CDN 延迟不否定已完成的数据更新和 Git 发布。

## 当前短期接受的非阻断问题

以下问题只在本轮“数据更新 + 最小发布包”运行范围内短期接受，不属于规则豁免；每日仍需记录原始数量。恢复完整报表更新前，或问题开始影响正常运行策略时，必须重新评估阻断等级。

| 问题 | 当前范围与业务影响 | 发布边界 | 后续责任节点 |
| --- | --- | --- | --- |
| 已披露基准尚无法确定权益分档 | 7 条；权益分档保持空值，相关资产分类筛选不完整 | 不猜测、不填经验比例，其余已核验字段可发布 | `index_benchmark` |
| 当前持仓同类排名不完整 | 5 条，当前最小包均属于停止或测试策略；对应前 50% 仓位比例只能按已覆盖部分解释 | 页面保留缺口披露，缺失项不得按前 50% 计入；若出现正常运行策略缺口，升级为显式修复任务 | `fund_nav`、`report_build` |
| 基金详情净值图不足 | 74 只不足两个有效净值点 | 不绘制伪造曲线，详情页明确显示无可用走势图 | `fund_nav`、`report_build` |
| FOF 历史完整性待确认 | 0 只成熟产品存在明确历史缺口；227 只缺成立日期，暂不能判断历史是否完整 | 只标记待确认，不把待确认对象写成已完整或已缺失 | `fund_nav`、`index_benchmark` |
| 重要策略元数据缺失 | 缺失率 5.78%，影响成立日期、风险、费率和基准筛选 | 缺失字段保持为空并显示覆盖率，不阻断其他准确数据 | `gffunds_metadata`、`report_build` |
| 临时报表源存在超 160 MiB 原始包 | 临时源不直接发布；实测最小发布包已 gzip/分片，最大正式数据文件约 3.06 MiB | 只允许最小包清单内压缩文件进入发布仓库 | `report_build`、`publish` |

## 最终状态与退出码

- `success`：全部成功，退出码 0。
- `success_with_warning`：数据可用，存在非阻断 warning，退出码 0。
- `partial_success`：至少一个渠道失败，但另一个渠道和核心加工交付成功，退出码 2，用于调度告警，不代表流程在失败点提前退出。
- `data_success_publish_failed`：数据和最小发布源成功，但最小包构建、校验、Git 提交或推送失败，退出码 2。单独的 Pages 传播验证失败只产生 warning。
- `failed_critical`：关键数据链路失败，退出码 1。

运行摘要位于：

```text
运行状态/logs/daily_update/<日期>/<run_id>/summary.json
运行状态/logs/daily_update/<日期>/<run_id>/summary.md
```

摘要会列出失败关键节点、失败发布节点、失败渠道节点、warning、skipped 节点、渠道采集及入库状态。

## 日志和备份保留

- 成功或只有 warning 的运行日志默认保留 30 天。
- 失败、部分成功和未正常收尾的运行日志默认保留 90 天，方便追因。
- 启动器 transcript 与每日节点日志内容重复，默认只保留 30 天。
- 每日最小发布脚本日志直接写入本批 `publish` 节点目录，随每日运行日志统一保留，不再额外形成无界日志目录。
- 当前批次和锁文件指向的活动批次永不清理。
- 清理范围仅限 `运行状态/logs/daily_update` 下达到保留期的完整批次目录，以及 `运行状态/logs/launcher` 下达到保留期的 `.log`；每次清理会生成结构化结果。
- 成功数据库备份默认滚动保留 2 个；不通过校验的 partial/failed 文件不进入成功版本，缺少元数据且超过 24 小时的自动命名孤儿备份会被清理。

保留参数集中在 `config/daily_update_policy.json`，不要通过删除日志或备份校验来规避空间问题。

## 中断后恢复

```bat
00_每日数据更新并发布_唯一入口.bat resume <run_id>
```

恢复模式必须与原批次的 dry-run/真实运行模式一致。不要在另一个每日批次仍持有 `daily_update.lock` 时强行恢复。

## 上线验收

代码修改后先执行节点框架、事务回滚、报表切换、日志保留和备份测试，再执行：

```powershell
python -X utf8 节点脚本\_共享组件\生产程序\运行项目数据稽核hook.py --mode manual
```

正式定时任务启用前，至少连续手工运行两次唯一入口并确认：

- 两次均无关键失败。
- 第二次主要执行增量或缓存复用，没有重复全量删除/重载。
- 最小发布集清单、页面数据日期和数据库水位一致；暂停更新的正式完整 `reportRoot` 未被本批覆盖。
- 备份、日志保留、发布及 Pages 验证结果符合预期。
