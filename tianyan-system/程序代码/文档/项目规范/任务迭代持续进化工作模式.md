# 任务迭代持续进化工作模式

## 核心原则

本项目不把 hook 当成一次性检查，而是把它作为任务闭环的一部分。每次修改都要经历：

1. 识别规则：先判断本次任务涉及哪些实体、字段、页面和质量规则。
2. 按规则执行：实现时按已有口径、字段字典、数据稽核规则处理。
3. 按规则检查：执行后运行对应层级 hook。
4. 解释问题：所有 error/warn 都要说明原因、影响、优化建议和责任脚本。
5. 沉淀规则：发现新问题类型时更新规则库和检测逻辑，避免下次重复。

## 检查层级

### Quick

适用场景：文档、小范围脚本修改、只验证现有页面包。

```powershell
python -X utf8 scripts\run_project_data_audit_hook.py --mode manual --audit-only
```

覆盖：

- Python/JS/PowerShell 静态检查。
- SQLite quick_check。
- 页面包字段重复、行宽、业务键重复。
- 基金经济暴露、AI 实体暴露和业务质量 warning。

### Full

适用场景：采集、加工、字段口径、页面包、实体识别、报表展示、策略治理、基金暴露等任何业务逻辑修改。

```powershell
python -X utf8 scripts\run_project_data_audit_hook.py --mode manual
```

覆盖：

- Quick 全部检查。
- 重建 basic_data 报表包。
- 重建字段字典、质量包、主题包、基金详情增强包。
- 刷新部署清单。

### Strict

适用场景：准备交付、同步到内网服务器、合并大量数据改动。

```powershell
python -X utf8 scripts\run_project_data_audit_hook.py --mode manual --fail-on-warn
```

覆盖 Full，并把 warning 也作为失败处理。

## 自迭代规则

### 新问题必须规则化

如果 hook 输出 `RULE_CATALOG_MISSING`，说明某个问题没有登记到：

- `config/数据稽核规则规范.json`
- `config/系统字段检查规则.json`

处理方式：

1. 为问题新增稳定 `ruleId`。
2. 写清楚原因说明、优化建议、修复责任脚本。
3. 若问题涉及核心表字段、页面包字段、字段覆盖率或字段字典实体，同步更新 `config/系统字段检查规则.json`。
4. 在 `scripts/标准化数据稽核.py` 或 `scripts/运行项目数据稽核hook.py` 中补检测逻辑。
5. 重新运行 hook。

凡增量更新会重新生成业务事件ID的派生事实，必须同时具备“后置原子重建 + 构建状态表 + 事件集合/最新日期稽核 + 页面同事件ID产物稽核”。不得仅依赖历史派生表继续匹配新事件，也不得只验证数据库而忽略最终详情包是否生成可用曲线。

### 持续问题必须升级

如果 hook 输出 `PERSISTENT_AUDIT_ISSUE`，说明同一问题在最近多次 hook 中持续出现。

处理方式：

1. 若影响业务判断，直接修复。
2. 若短期接受，必须在最终说明中写明业务影响和后续处理计划。
3. 不允许长期用“已有 warning”解释而不推进。

## 效率策略

- `pre-commit` 和 `pre-push` 默认走 `audit-only`，避免每次提交都重建 1GB+ 页面包。
- `post-commit`、`post-merge`、`post-checkout` 默认走 Full，用于自动刷新和完整闭环。
- 人工或 Codex 修改业务逻辑后，应优先跑 Full。
- 只改文档或注释时，可跑 Quick，但最终说明要说明使用了 Quick 的原因。
- 准备交付或同步内网前跑 Strict。

## 最终答复要求

每次任务完成时必须说明：

- 本次适用的检查层级。
- 标准化稽核状态。
- 业务质量 warning/error。
- 新增或更新了哪些规则。
- 最新 hook summary 和 data audit 报告路径。
