# 策略列表页“业务分类”字段血缘与计算口径

## 1. 文档目的

本文说明策略列表页字段“业务分类（运营货架口径，可能比研报产品类型更细）”的完整数据血缘、输入来源、计算公式、判断优先级、落地位置和当前数据情况。

本文描述的是截至 2026-07-28 当前生产代码的实际行为。若字段字典文字、Python 初始分类和 JavaScript 最终分类存在差异，以最终写入正式页面数据包的 JavaScript 结果为当前页面事实口径，并在本文中单独披露差异。

适用范围：

- 正式策略列表页。
- AI 选策略页面中的业务分类筛选。
- 数据洞察页面中的业务分类统计。
- 策略详情页中的业务分类和业务分类依据。
- 调仓事件、经营分析等从策略主数据包继承业务分类的报表。

## 2. 核心结论

### 2.1 是否保存在数据库

当前 SQLite 主库 `数据库/analysis_zh_current.sqlite` 中没有持久化字段：

- `业务分类`
- `业务分类依据`
- `研报产品类型`
- `研报股票子类型`

数据库表 `策略信息` 保存的是渠道原始信息和标准化主档，包括：

- `统一策略ID`
- `渠道ID`
- `渠道策略ID`
- `策略名称`
- `投顾机构`
- `策略类型`
- `风险等级`
- `成立日期`
- `建议持有时长`
- `起投金额`
- `投顾费率`
- `业绩基准`
- `标签JSON`
- `策略状态`
- `策略描述`
- `原始来源URL`
- `原始快照ID`
- `首次入库时间`
- `最近入库时间`

因此，数据库中的 `策略类型` 是渠道披露字段，不等于页面的 `业务分类`。

### 2.2 实际保存位置

“业务分类”在报表构建阶段动态生成，最终保存到页面数据包：

| 数据层 | 保存状态 | 当前路径或对象 |
|---|---|---|
| SQLite 主库 | 未保存 | `数据库/analysis_zh_current.sqlite` |
| 正式完整汇总包 | 已保存 | `结果文件/全市场投顾分析平台/basic_data/data/basic_summary.js` |
| 正式核心汇总包 | 已保存 | `结果文件/全市场投顾分析平台/basic_data/data/basic_summary_core.js` |
| 策略详情包 | 已保存 | `结果文件/全市场投顾分析平台/basic_data/data/details/<统一策略ID>.js` |
| 最小发布包 | 已保存 | `结果文件/最小发布集/basic_data/data/basic_summary_core.js.gz` |
| 调仓/洞察衍生包 | 按需要复制 | 调仓事件、洞察和专题数据包中的策略维度字段 |

页面前端不再计算分类，只读取数据包中的 `业务分类`，并用完全相等条件筛选：

```javascript
if (business && row.业务分类 !== business) return false;
```

### 2.3 字段定位

`业务分类`回答的是：这个策略在运营货架、产品线和销售场景中属于哪一类。

`研报产品类型`回答的是：这个策略应进入哪个资产和业绩比较池。

二者不是同一字段，也不是一一对应关系。例如：

- “目标盈系列产品”可以同时包含纯债型、固收+型、股债混合型、股票型和多元配置型。
- “现金管理型”在业务货架上单独列示，但当前研报口径会进入“纯债型”。
- “信号类策略”按执行机制单独列示，但研报类型仍可能是股票型、纯债型或多元配置型。

当前正式页面导出包含以下渠道：


即：

- `ttfund`：天天基金/投顾。
- `gffunds`：广发基金投顾。

## 6. 持仓选择逻辑

### 6.1 直接持仓

对于 `策略当前持仓`，按每个 `统一策略ID` 选择最大 `持仓日期` 对应的正权重记录。

### 6.2 推算持仓

对于 `策略当前持仓推算补齐`，按每个 `统一策略ID` 选择最大 `推算持仓日期` 对应的记录。

### 6.3 两种持仓的优先级

当前代码的选择规则为：

```text
如果该策略存在推算持仓：使用推算持仓
否则：使用直接披露持仓
```

也就是说，当前实现不是简单比较两个日期后取更新者，而是只要存在推算持仓就优先使用推算持仓。页面会在分类依据中标记：

- `持仓来源=推算持仓`
- `持仓来源=直接披露持仓`
- `持仓来源=未取得权重`

## 7. 持仓权重标准化

设某策略所有正权重持仓的原始权重合计为：

```text
S = Σ raw_weight_i
```

标准化系数为：

```text
如果 S <= 1.5：
    scale = 100

如果 S < 80 或 S > 105：
    scale = 100 / S

否则：
    scale = 1
```

每只基金参与分类的权重为：

```text
weight_i = raw_weight_i × scale
```

含义：

- 合计接近 1 的数据视为小数比例，例如 0.35 转换为 35%。
- 合计明显偏离 100 的数据重新归一到 100%。
- 合计位于 80% 至 105% 的数据保留源端披露值，不强制补足现金或压缩到100%。
- 权重为空、等于0或小于0的持仓不参与分类。

## 8. 基金资产桶计算

每只持仓基金通过 `基金标准分类字典` 和持仓披露字段归入一个主资产桶。

判断字段包括：

- 基金名称、基金简称。
- 天天基金细分类、大类、二级分类。
- 标准资产大类、标准资产细类。
- 投顾资产分类桶。
- 持仓资产类型、分组名称。
- 是否货币基金、是否商品黄金、是否债券基金、是否权益基金、是否混合基金。

主资产桶判断顺序为：

1. 货币/现金。
2. 商品/黄金。
3. 债券。
4. 权益。
5. 混合。
6. 未知。

该顺序有实际影响。例如某只基金同时出现多个关键词时，先命中的资产桶生效。

定义：

```text
E = 权益基金权重 = Σ weight_i，其中 fund_bucket_i = equity
B = 债券基金权重 = Σ weight_i，其中 fund_bucket_i = bond
C = 货币基金权重 = Σ weight_i，其中 fund_bucket_i = cash
M = 混合基金权重 = Σ weight_i，其中 fund_bucket_i = mixed
G = 商品黄金权重 = Σ weight_i，其中 fund_bucket_i = commodity
U = 未知基金权重 = Σ weight_i，其中 fund_bucket_i = unknown
```

## 9. 交叉属性权重

QDII、指数、主动和FOF不是互斥资产桶，而是叠加在主资产桶上的工具属性。

定义：

```text
Q = QDII权重
I = 指数基金权重
A = 主动基金权重
F = FOF权重
```

计算规则：

```text
Q = Σ weight_i，基金满足“是否QDII”或市场地域标签含海外、全球、港股、美国

I = Σ weight_i，基金满足是否指数基金、ETF、ETF联接或指数增强

A = Σ weight_i，基金主动被动标签包含“主动”

F = Σ weight_i，基金满足是否FOF
```

因此：

- 一只QDII股票基金的权重可以同时计入 `E` 和 `Q`。
- 一只海外指数基金的权重可以同时计入 `E`、`Q` 和 `I`。
- 不应把 `E+B+C+M+Q+I` 相加后与100%比较，因为Q、I是重叠属性。

## 10. 基准权重和海外证据

### 10.1 Python 初始阶段

初始导出阶段从 `策略基准资产配置` 或业绩基准公式中取得：

```text
BE = 基准权益权重
BB = 基准债券权重
BC = 基准货币权重
BH = 基准海外权重
```

Python 初始分类中的有效资产中枢为：

```text
有效权益 = max(E + 0.5 × M, BE)

有效债券货币 = max(B + C + 0.5 × M, BB + BC)
```

这两个“有效”指标只用于初始主可比池。最终 JavaScript 业务分类会重新判断并覆盖结果。

### 10.2 最终页面阶段

最终页面业务分类主要使用实际持仓权重 `E、B、C、M、Q、I`。

基准权重直接参与最终业务分类的主要场景是海外识别：

```text
海外主证据 = Q >= 30
            或 海外基准权重 >= 30
            或 策略名称/披露策略类型命中强海外词
```

海外混合证据为：

```text
海外混合证据 = 海外主证据
              或 Q >= 10
              或 海外基准权重 >= 10
```

明确海外词包括：

- QDII
- 海外
- 港股、美股
- 恒生
- 纳斯达克、纳指
- 标普、S&P
- 美国、印度、越南、日本、德国
- 日经、DAX
- 有明确资产或市场含义的“全球”

排除项：

- “兴证全球”作为机构品牌时不认定为海外配置。
- MSCI沪深300、MSCI中国A股、MSCI中国不认定为海外。
- 通用合同投资范围不单独触发海外分类。
- 黄金、商品不等于海外资产。

最终业务分类使用的文本可概括为：

```text
T = 策略名称
  + 策略概念
  + 策略描述
  + 特殊标签
  + 披露策略类型
  + 详情补充识别文本
  + 策略治理状态
  + 分析分组
  + 治理规则说明
```

详情补充文本会读取：

- 策略名称。
- 策略概念。
- 策略描述。
- 特殊标签。
- 披露策略类型。
- 合同、协议、服务条款、策略说明等原始资料字段。

为避免分类结果自我引用，详情补充文本明确排除以下派生字段：

- 业务分类。
- 业务组合分类。
- 业务分类标签。
- 业务分类依据。
- 分类依据。
- 风险分类依据。
- 风险等级。
- 策略实现标签。
- 天天展示类派生字段。

但策略汇总行中已有的 `特殊标签` 仍会参与最终判断，因此初始分类产生的主题、目标盈、海外等特殊标签可能继续成为最终分类证据。

## 12. D0持仓缺失判断

最终报表构建会先重新计算系统风险等级。

如果以下字段全部为0或缺失：

```text
E、B、C、M、I
```

则：

```text
风险等级 = D0 持仓缺失
```

D0策略的处理结果：

- 保留在数据补齐和策略列表原始数据中。
- `研报产品类型`设为“持仓缺失/不入池”。
- 不进入市场总览、仓位分析和调仓主图。
- 业务分类通常保留初始分类；但当前实际代码在D0判断之前先执行目标日期、信号和目标盈文本判断，详见下一节。

## 13. 最终“业务分类”实际计算规则

### 13.1 重要说明

最终页面业务分类由 `apply_field_renames_and_build_insights.js` 中的 `canonicalBusiness()` 计算，并覆盖 Python 初始导出的业务分类。

下面列出的顺序是当前代码真实执行顺序。命中前一条后立即返回，不再继续判断后续分类。

### 13.2 实际优先级

| 顺序 | 最终业务分类 | 实际判断条件 | 业务含义 |
|---:|---|---|---|
| 1 | 目标日期/养老型 | `T`命中目标日期、养老、生命周期 | 长期养老、目标日期产品线 |
| 2 | 信号类策略 | 命中明确信号、分笔、发车、跟车、买卖或止盈执行机制 | 提供操作信号，不按普通组合调仓解释 |
| 3 | 目标盈系列产品 | 命中强目标盈品牌；或同时命中目标收益机制和生命周期退出证据 | 按目标达标和期次运营的产品线 |
| 4 | 保留原分类/未分类 | 风险等级为D0，或 `E、B、C、M、I`全部为0 | 缺乏稳定资产权重，不新做资产分类 |
| 5 | 现金管理型 | `C >= 80` | 货币基金占绝对主导 |
| 6 | 纯债/短债型 | `B + C >= 90` 且 `E < 10` | 债券、短债、货币货架 |
| 7 | 海外/全球型 | `Q >= 30`，或海外基准>=30，或有强海外文本 | 海外或全球配置主导 |
| 8 | 主题/行业型 | `T`命中明确行业或主题词 | 行业主题营销和投研跟踪 |
| 9 | 偏股配置型 | `E >= 40` 或 `I >= 45` | 偏权益或指数工具主导 |
| 10 | 固收增强型 | `B + C >= 70` 且 `E < 40` | 固收为底仓并含增强资产 |
| 11 | 多资产配置型 | `M >= 20` 或 `E >= 15` 或 `Q >= 5` | 多类资产共同参与 |
| 12 | 保留原分类/未分类 | 均未命中 | 使用初始业务分类作为兜底 |

### 13.3 目标日期/养老型

命中表达式：

```text
目标日期 | 养老 | 生命周期
```

一旦命中，优先于信号、目标盈和资产权重规则。

### 13.4 信号类策略

以下强品牌或机制可以直接触发：

- 薪动月月投。
- 超级定投家。
- 指数100份。
- 信号类、信号服务。
- 债市信号指导。
- 买入信号、卖出信号、建议信号、止盈信号、买卖全程信号。

以下机制需要组合命中：

```text
智能发车、滚动带投、发车带投、带你买卖
+
买卖点、买卖、卖出、止盈、信号
```

或者：

```text
100份、等额划分、分笔管理、分批投
+
发车、买卖、带投、止盈、加倍投入、信号
```

一般性的“信号”一词只有同时出现买入、卖出、止盈、发车、跟车、加倍投入、带投或买卖等执行词时才触发。

### 13.5 目标盈系列产品

强品牌词包括：

- 目标盈。
- 小目标。
- 小赢家。
- 小杏运。
- 步步高。
- 小星愿。
- 小盈加。
- 智盈。
- 智慧目标投。
- 小常乐、常乐。

命中任一强品牌即可触发。

没有强品牌时，必须同时满足：

```text
明确目标收益/达标止盈机制
+
生命周期或退出证据
```

明确目标收益/止盈机制包括：

- 目标收益、收益目标、绝对收益目标。
- 目标止盈、止盈目标。
- 达标即止盈、达标止盈、止盈达标。
- 达到目标、目标达成。
- 达标退出、达标赎回。

生命周期或退出证据包括：

- 期次、第N期。
- 到期、期满、运作期、封闭期。
- 续作、赎回、退出。
- 发售、发行、自动终止。
- stopped。
- 一年期、两年期、年中版、新年特供。

只有普通止盈止损、预期兑现后止盈、一般风险控制或只有到期日期，不应单独认定为目标盈系列。

- 医药、医疗。
- 消费。
- 新能源。
- 半导体。
- 军工。
- 科技、AI、人工智能。
- 红利。

## 14. “原分类”兜底从哪里来

最终 JavaScript 中的原分类按以下顺序取得：

```text
业务分类
→ 业务主分类
→ 主可比池
→ 未分类
```

这些值通常来自 Python 初始导出阶段。

Python 初始主可比池使用：

```text
有效权益 = max(E + 0.5M, BE)
有效债券货币 = max(B + C + 0.5M, BB + BC)
```

初始分类顺序为：

1. 目标日期/养老型。
2. 目标盈系列产品。
3. 海外/全球型。
4. 主题/行业型。
5. 现金管理型：`max(C, BC) >= 80`。
6. 纯债/短债型：有效债券货币>=90且有效权益<10。
7. 固收增强型：有效债券货币>=70且有效权益<40。
8. 偏股配置型：有效权益>=60。
9. 多资产配置型。

若策略治理标签确认 `是否信号类组合=1`，Python 初始阶段会再覆盖为“信号类策略”。

注意：初始 Python 阈值与最终 JavaScript 阈值不完全一致。例如偏股配置初始阈值为有效权益>=60%，最终页面阈值为实际权益>=40%或指数>=45%。最终页面以 JavaScript 覆盖后的结果为准。

典型输出：

```text
实际货币基金权重100.00%，达到80%现金管理阈值。
```

```text
实际债券+货币权重93.96%，权益3.74%，按纯债/短债货架分类；披露策略类型不改变该判断。
```

```text
权益55.04%、指数0.00%，偏权益资产占主导。
```

```text
强海外证据归属：QDII/海外持仓98.60%，海外基准95.00%；通用投资范围、机构品牌和黄金/商品不触发海外分类。
```

```text
名称或介绍包含目标盈/小目标/小杏运品牌、期次，或明确目标收益/达标止盈/到期赎回机制，按目标达标运营池分类；普通止盈止损、预期兑现后止盈或仅含到期时间不归入目标盈。
```

## 16. 研报产品类型计算

### 16.1 字段定位

研报产品类型是资产和调仓分析比较口径，当前取值包括：

- 纯债型。
- 固收+型。
- 股债混合型。
- 股票型。
- 多元配置型。
- 持仓缺失/不入池。

### 16.2 实际执行顺序

| 顺序 | 研报产品类型 | 判断条件 |
|---:|---|---|
| 1 | 持仓缺失/不入池 | 风险等级为D0 |
| 2 | 股票型 | `E >= 70` |
| 3 | 多元配置型 | 存在多资产特征，并且 `Q >= 10`、海外基准>=10或有海外主证据 |
| 4 | 纯债型 | `E < 1` 且 `B + C >= 80` |
| 5 | 固收+型 | `E <= 20` |
| 6 | 股债混合型 | `E < 70` |
| 7 | 多元配置型兜底 | `M >= 20` 或存在多资产特征 |
| 8 | 股债混合型兜底 | 其他情况 |

“多资产特征”包括：

- QDII或海外混合证据。
- 名称或标签包含多资产、多元、黄金、商品、原油、REIT、另类、全天候。

注意：按当前代码结构，前面的 `E >= 70` 和后面的 `E < 70` 已覆盖所有正常数值，因此第7、8条后置兜底在正常数值下实际上很难到达。当前页面中的“多元配置型”主要由第3条海外/多资产分支产生。

### 16.3 股票子类型

仅当 `研报产品类型=股票型` 时继续分类，顺序为：

1. QDII型：有海外主证据或 `Q >= 20`。
2. 行业主题型：命中行业、主题、医药、消费、新能源、科技等主题词。
3. 行业轮动：命中轮动、赛道、趋势、择时、风格、行业切换、主题切换。
4. 指数驱动：`I >= 45`，或命中指数、ETF、联接、增强、宽基等词。
5. 主动优选：均未命中时的兜底。

## 17. 业务分类与研报类型为什么会不同

业务分类优先表达产品线、销售场景和执行机制；研报产品类型优先表达资产结构。

例如目标盈策略先被业务规则归入“目标盈系列产品”，但它仍会根据权益权重进入不同研报类型：

```text
目标盈系列产品
  ├─ 权益很低且债券货币占主导 → 纯债型或固收+型
  ├─ 权益处于中间区间 → 股债混合型
  ├─ 权益达到70%以上 → 股票型
  └─ 有显著海外/多资产特征 → 多元配置型
```

这正是页面提示“运营货架口径，可能比研报产品类型更细”的具体含义。

### 20.1 当前数量

截至 2026-07-28 当前数据库：

|---|---:|
| 数据库全部渠道 | 1,349 |

|---|---:|

差异：

```text

```

缺少的74条全部为 `gffunds` 策略，主要是 `gffunds__ZY...` 目标盈期次策略。

### 20.2 根因

页面包内部记录的基础生成时间为：

```text
2026-07-24 00:30
```

缺少的74条广发策略首次入库时间为：

```text

```

后续运行了报表包二次构建，文件修改时间被刷新，但二次构建脚本只读取既有 `basic_summary.js` 并重算分类、洞察和拆包，不会重新从 SQLite 查询策略主列表。因此：

```text
页面文件修改时间较新
≠
页面基础策略清单已经从当前数据库重新导出
```

### 20.3 影响

- 当前已有1,137条页面策略都有业务分类。
- 新入库的74条广发策略没有进入当前页面包，因此页面中没有这些策略的业务分类记录。
- 广发目标盈系列数量、产品线覆盖、经营分析和策略筛选会少计。
- 只查询页面数据包会得到1,137条；只查询数据库展示渠道会得到1,211条，两者当前不一致。

### 20.4 正确刷新顺序

应先重新从数据库生成基础页面，再进行二次加工：

```powershell
python -X utf8 程序代码\节点脚本\_共享组件\生产程序\export_basic_data_pages.py --db-path 数据库\analysis_zh_current.sqlite --site-dir 结果文件\全市场投顾分析平台\basic_data

python -X utf8 程序代码\节点脚本\_共享组件\生产程序\build_basic_data_report_packs.py --report-root 结果文件\全市场投顾分析平台
```

实际执行时应以节点化生产入口和脚本当前参数帮助为准，不应绕过生产节点资源锁直接与正在运行的更新任务并发写页面包。

## 21. 当前实现存在的口径风险

### 21.1 分类结果没有数据库持久化

影响：

- SQL不能直接查询业务分类。
- 每次页面构建都要重新计算。
- 页面包未刷新时，新入库策略没有业务分类。
- 无法方便追踪某策略的分类何时、因为什么规则发生变化。

建议增加分析快照表，而不是直接污染渠道原始主档。例如：

```text
策略业务分类快照
  - 统一策略ID
  - 分类版本
  - 分类生成时间
  - 业务分类
  - 业务分类依据
  - 研报产品类型
  - 研报股票子类型
  - 持仓来源
  - 持仓日期
  - 权益/债券/货币/混合/QDII/指数权重
  - 基准海外权重
  - 规则命中编码
  - 输入证据摘要或指纹
```

### 21.2 Python与JavaScript存在两套规则

当前至少存在：

- Python 初始主可比池规则。
- JavaScript 最终业务分类规则。

两者的阈值和顺序不完全一致，例如：

| 项目 | Python 初始规则 | JavaScript 最终规则 |
|---|---|---|
| 偏股配置 | 有效权益>=60% | 实际权益>=40%或指数>=45% |
| 混合基金处理 | 权益和固收各计50% | 最终业务分类直接使用独立M，不折半进入E/B |
| 信号策略 | 治理标签覆盖 | 文本规则再次识别 |
| 基准权重 | 广泛参与初始资产中枢 | 最终业务分类主要只用于海外证据 |

最终页面虽有明确覆盖顺序，但维护者若只修改其中一套规则，容易造成：

- 初始详情和最终列表短暂不一致。
- 业务分类依据与分类值来自不同阶段。
- 局部报表调用初始数据时得到不同结果。

建议把最终规则集中到一个版本化配置和一个共享分类实现中，Python和JavaScript只消费结果，不各自维护阈值。

### 21.3 字段字典描述顺序与代码顺序略有差异

页面字段字典把D0持仓缺失描述为优先处理，但实际 `canonicalBusiness()` 的顺序为：

```text
目标日期 → 信号 → 目标盈 → D0/持仓缺失 → 资产规则
```

因此D0策略如果名称先命中目标盈、信号或目标日期，业务分类仍可能保留该产品线分类，但研报产品类型会是“持仓缺失/不入池”。当前页面中确实存在这种组合。

建议统一字段字典文字和代码顺序，并明确：

- D0是否完全禁止重新分类。
- 还是允许保留产品线分类，但禁止进入资产比较池。

从业务含义看，后者更合理，但必须在字段字典中明确写出。

### 21.4 研报多元配置后置兜底近似不可达

当前代码先判断 `E >= 70`，随后又判断 `E < 70`。正常数值已被覆盖，所以更后面的“混合>=20或存在多资产特征则多元配置”分支基本不可达。

当前多元配置型主要依赖前置海外/多资产分支产生，可能使纯国内多资产策略进入股债混合型而不是多元配置型。

建议重新整理为明确互斥决策表，并为每个分支增加单元测试。

### 21.5 稽核未发现页面策略数量漂移

最新标准化数据稽核状态为：

```text
status=warn
error=0
warn=6
```

但当前稽核没有报告数据库展示渠道1,211条与页面包1,137条的差异。

建议新增规则：

```text
PAGE_DISPLAY_STRATEGY_COUNT_MISMATCH
```

检查内容至少包括：

- 数据库展示渠道策略ID集合。
- `basic_summary.js`策略ID集合。
- `basic_summary_core.js`策略ID集合。
- 最小发布压缩包策略ID集合。
- 缺失ID、额外ID、渠道分布和首次入库时间。

## 26. 维护原则

后续修改业务分类时，应同时满足：

1. 每个策略只有一个互斥 `业务分类`。
2. 产品线分类与资产比较分类分开，不把“目标盈、信号、养老”强行当成资产类型。
3. 海外分类必须有持仓、基准或明确境外市场文本证据，不能由机构品牌或通用合同范围触发。
4. 缺少持仓时不得虚构资产比例。
5. `业务分类依据`必须能解释具体命中规则和关键数值。
6. 分类规则必须有版本号、单元测试和页面/数据库集合一致性检查。
7. 修改分类、字段字典或页面包后，必须重新生成受影响数据包并执行标准化数据稽核。
8. 页面发布前必须核对数据库策略ID集合、正式页面包和最小发布包一致。
